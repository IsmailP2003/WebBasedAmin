Abstract
This project addresses the technological disparity faced by small scale educational institutions, which often lack the resources to implement enterprise level Management Information Systems (MIS). The study details the design, implementation, and evaluation of a centralised, web-based School Administration System using the MERN stack (MongoDB, Express.js, React, Node.js). Adopting a hybrid software development methodology, the project successfully delivers a functional Minimum Viable Product (MVP) capable of handling student enrolment, course scheduling, and academic grading. Critical evaluation using the System Usability Scale (SUS) demonstrates that bespoke, lightweight web applications can offer a viable, cost-effective alternative to disjointed legacy systems, effectively resoling the data silos problem.

Introduction
1.1 Project Background
Administrative processes are fundamental to the effective running of any educational institution. Tasks such as maintaining student records, recording attendance, managing course information, and tracking academic progress all depend on information being accurate, accessible, and easy to update. Where these processes are managed well, staff are better able to work efficiently and make informed decisions. Where they are managed poorly, duplication, inconsistency, and delay can become routine.
The wider educational sector has seen substantial growth in the use of digital technology, not only in teaching and learning but also in system management and institutional administration (UNESCO, 2023). However, access to well-designed digital systems is not always consistent across educational settings. While larger institutions may be able to adopt comprehensive enterprise platforms, smaller schools, tuition centres, training providers, and similar organisations may instead rely on a mixture of spreadsheets, paper files, email chains, and separate digital tools. Although these approaches may be workable on a small scale, they often become inefficient and difficult to manage as the volume of administrative data increases.
This fragmented way of working creates several practical problems. The same information may be recorded in multiple places, increasing the likelihood of duplication and inconsistency. Staff may need to re-enter data, cross-check records manually, or move between disconnected tools in order to build a complete picture of a student’s details, attendance, or performance. This does not only reduce efficiency; it also affects reliability and visibility. Research on student and education management information systems suggests that factors such as system quality, information quality, and service quality have a direct effect on user satisfaction and successful use of such systems (Gürkut and Nat, 2018; Martins et al., 2019). This makes the quality of the underlying administrative platform an important issue rather than a purely technical preference.
The problem is also significant from a professional and ethical perspective. School administration systems process personal and academic information, and in many cases this concerns children or young people. As a result, privacy, access control, and responsible data handling are central design concerns rather than optional add-ons (Information Commissioner’s Office, 2023). In addition, because the proposed solution is web-based, it should be designed with accessibility and security in mind. Current guidance such as WCAG 2.2 emphasises the need to make web content more accessible to a wide range of users, while OWASP identifies broken access control and related weaknesses as among the most critical risks affecting web applications today (W3C, 2024; OWASP Foundation, 2025).
This project responds to these issues through the development of a centralised web-based school administration system. The system is intended as a proof-of-concept minimum viable product (MVP) that brings together core administrative functions in a single application. Instead of relying on separate tools for student details, attendance, courses, and grades, the project explores whether these functions can be managed more effectively through one integrated platform. The purpose is not to reproduce every feature of a commercial school management product, but to investigate whether a focused and well-designed web application can provide a practical response to the inefficiencies created by fragmented administrative processes.
From a software engineering perspective, the project provides a realistic opportunity to investigate a real organisational problem through full-stack system development. It involves requirements analysis, database design, authentication, interface design, implementation, testing, and evaluation. It also requires consideration of wider professional issues, including data protection, usability, security, accessibility, and Equality, Diversity and Inclusion (EDI). For this reason, the dissertation takes a proof-by-construction approach: rather than discussing the problem only in abstract terms, it develops and evaluates a working software artefact in order to assess the feasibility and usefulness of the proposed solution.

1.3 Scope and Boundaries
As this project is being completed within the constraints of an individual final-year dissertation, it is necessary to define clear boundaries. The system is therefore developed as an MVP rather than a full institutional platform. The purpose of the project is to create and evaluate a focused administrative core, not to replicate the full range of features found in large commercial school management systems.
The current implementation is centred on the Administrator role. This means the system is designed primarily to support the creation, maintenance, and management of student records, course information, attendance data, and grades from an administrative perspective. This boundary has been chosen deliberately in order to keep the project achievable while still addressing the main problem identified in the background discussion. Although teachers, students, and parents would be relevant stakeholders in a broader real-world system, they are outside the scope of the present implementation.
For the same reason, several features commonly associated with larger educational platforms are not included in this version of the system. These include parent and student portals, messaging tools, timetabling, payment processing, mobile-native applications, and advanced analytics. Their exclusion is a matter of scope control rather than a judgement on their value. The intention is to establish a solid administrative foundation that could be extended in future work.
The project is also limited by the timeframe and resources available for development. As a result, the system is evaluated primarily as a prototype and proof of concept. It is intended to demonstrate sound design decisions, functional correctness, and practical usefulness, rather than full enterprise readiness or large-scale deployment.
1.4 Development Approach
The project adopts a hybrid development approach combining incremental development with iterative prototyping. This approach is appropriate for an individual software engineering project with a fixed submission deadline. A fully sequential approach would provide structure, but it would offer less flexibility when refining the interface and responding to issues discovered during development. A fully agile team-based process would also be less suitable given the scale and context of the project. A hybrid model provides a practical balance between control and adaptability.
The system is developed incrementally by building the main functional areas in stages. Core features such as authentication, student management, course management, attendance, and grade handling can therefore be implemented and tested as distinct parts of the system. At the same time, the user interface is refined iteratively through prototyping, allowing layout, navigation, and usability decisions to improve as development progresses.
This approach supports both the technical and investigative aims of the dissertation. It makes it possible to manage the development process in a structured way while still allowing the system to evolve in response to technical findings and evaluation feedback. The project is therefore treated not simply as a coding task, but as a software engineering investigation into whether the proposed solution is viable in practice.

2.2 Domain Analysis: The Operational Context
2.2.1 The Digital Divide in Educational Technology
The modern educational sector is characterized by an "information explosion," necessitating robust digital infrastructure to manage complex administrative ecosystems (Al-Emran et al., 2018). While the adoption of Educational Technology (EdTech) accelerated exponentially following the global shift to remote learning (Hodges et al., 2020), a significant technological disparity exists for smaller institutions. Research indicates that private tutoring centres, vocational colleges, and independent language schools are frequently priced out of the enterprise market due to insurmountable barriers to entry, primarily financial constraints and a lack of dedicated IT personnel (Peltier et al., 2012). Consequently, Selwyn (2020) observes that these institutions often adopt an approach of "bricolage"—a cobbling together of mismatched, ad-hoc digital and physical tools to manage daily operations. This digital divide forces smaller educational providers to operate with heightened administrative friction, limiting their ability to scale and effectively monitor student progress.
2.2.2 The "Data Silo" Architecture and Interoperability Failures
The direct technical consequence of the bricolage approach is the creation of "Data Silos." Laudon and Laudon (2020) define data silos as isolated repositories of data that remain inaccessible to other parts of an organization. From a technical perspective, this isolation is driven by schema incompatibility and a profound lack of Application Programming Interface (API) interoperability (Hasselbring, 2000). For instance, a student record stored within a proprietary finance spreadsheet operates on a fundamentally different data structure than the same student’s record in a physical attendance logbook. Without a unified backend architecture to facilitate state exchange, a modification in one system does not propagate to the others. This architectural failure directly violates the database principle of Referential Integrity, guaranteeing that data will eventually become desynchronised and corrupt over time, ultimately degrading the institution's operational efficiency.
2.2.3 The Prevalence and Risk of "Shadow IT"
A critical finding within the literature of organizational management is the widespread reliance on "Shadow IT"—systems and software utilised without explicit organizational approval or oversight (Rentrop and Zimmermann, 2012). In small educational settings, this predominantly manifests as the use of Microsoft Excel for complex relational data tasks. While spreadsheets offer high initial flexibility, they are notoriously error-prone when used as makeshift databases. In a seminal meta-analysis of spreadsheet accuracy, Panko (2008) discovered that 88% of unmanaged spreadsheets contain significant, compounding errors. Recent studies citing Panko continue to validate these high error rates, particularly in environments lacking strict version control (Silic and Back, 2014). Unlike a dedicated Database Management System (DBMS) that enforces ACID (Atomicity, Consistency, Isolation, Durability) transactions, a spreadsheet lacks internal constraints. A user can inadvertently delete a student from an enrolment tab while leaving their grades orphaned in another, creating a "Hidden Factory" of fragile macros and manual workarounds that pose a severe operational risk to the institution.
2.2.4 Critical Evaluation of Existing Market Solutions
To robustly justify the development of a bespoke administration system, it is necessary to critically evaluate the off-the-shelf solutions currently available on the market. The industry standard for UK state schools is Capita SIMS, a comprehensive Enterprise Resource Planning (ERP) system. However, SIMS traditionally operates as a legacy "thick client" Windows application, creating a significant barrier to remote access that often necessitates complex Virtual Private Networks (VPNs). Furthermore, the "Total Cost of Ownership" (TCO) for such enterprise systems frequently exceeds £20,000 per annum (Educause, 2022), rendering it financially unviable for small independent institutions. Beyond cost, Markus et al. (2000) note that schools using proprietary ERPs often suffer from extreme "Vendor Lock-in," where closed data formats make migrating away from the platform notoriously difficult, effectively trapping the institution's intellectual property and data assets.
Conversely, institutions often attempt to repurpose Learning Management Systems (LMS) such as Moodle or Blackboard. While these platforms excel at the pedagogical delivery of content, the literature highlights a fundamental conflation between an LMS and a Student Information System (SIS) (Weaver et al., 2008). Moodle lacks native, robust support for statutory census reporting, complex financial invoicing, or detailed staff HR management. Attempting to shoehorn these administrative features into an LMS via third-party plugins often destabilises the core platform, creating significant technical debt.

2.2.5 Cognitive Load, EDI, and Public Well-being
Software development in the modern era must consider Equity, Diversity, and Inclusion (EDI), alongside broader societal impacts such as public well-being. The usability of educational software is frequently cited as a critical failure point. Sweller’s (1988) Cognitive Load Theory posits that human working memory is strictly limited. When an interface is cluttered with irrelevant options—a common critique of legacy ERPs—"extraneous cognitive load" increases, leaving the user with less mental capacity for their actual tasks. By prioritising a minimalist, user-centric interface designed in accordance with established Human-Computer Interaction (HCI) heuristics (Norman, 1988; Nielsen, 1993), the proposed project directly addresses the "technostress" experienced by administrative staff. Reducing this digital friction contributes directly to public well-being by lowering teacher and administrator burnout, thereby improving the operational health of educational facilities.
Furthermore, compliance with the Web Content Accessibility Guidelines (WCAG 2.1) ensures the system remains usable by staff with visual or motor impairments, directly addressing EDI requirements (Acosta-Vargas et al., 2016). Architecting the solution as a responsive "thin client" web application also ensures equity of access; staff members are not required to possess expensive, high-end hardware to run the portal, democratising access to the system across diverse socio-economic backgrounds.
2.2.6 Legal Frameworks: GDPR, Data Privacy, and Participant Consent
The storage of sensitive student data introduces significant legal and ethical considerations regarding data subjects, strictly governed by the UK General Data Protection Regulation (GDPR). A primary ethical concern is the management of Participant Consent (Article 7). Educational institutions must capture and persistently maintain explicit, freely given consent for data processing, particularly concerning minors (Tikkinen-Piri et al., 2018). Ad-hoc manual systems and paper files frequently result in lost or untraceable consent forms. A digital, centralised system ensures that consent is explicitly logged as a mandatory boolean flag within the database schema, adhering to the highest ethical best practices of Privacy by Design (Cavoukian, 2009).
Additionally, Article 5 dictates that records must remain accurate, while Article 17 enforces the "Right to Erasure" (Hoepman, 2014). Conflicting records spread across digital spreadsheets and physical paper constitute an immediate breach of these articles. Ensuring every physical copy of a record is destroyed upon a user's request is operationally unfeasible in a siloed environment. A centralised database architecture solves this by enabling a single, global deletion command, facilitating the instant withdrawal of participant consent and ensuring total regulatory compliance.
2.3 Technical Review: Web Application Architectures
2.3.1 Data Processing Models and the MVC Architectural Pattern
At a foundational level, modern web applications rely on established architectural patterns to separate concerns and ensure maintainability. The Model-View-Controller (MVC) pattern, originally theorised by Reenskaug (1979) and modernized for enterprise application architecture by Fowler (2003), is widely accepted as the industry standard for full-stack development. Within the context of the proposed MERN stack, the MVC paradigm is distributed across the architecture: MongoDB acts as the Model representing the underlying data structures; React functions as the View, managing the user interface logic; and Express.js serves as the Controller, handling HTTP requests, input validation, and business logic routing. Adopting this strict separation ensures that future modifications to the UI do not inadvertently break the underlying database queries, a common vulnerability in older, tightly coupled architectures.
2.3.2 Architectural Paradigms: Monolithic versus Single Page Applications
The evolution of web delivery has seen a distinct shift from Multi-Page Applications (MPA) to Single Page Applications (SPA). Traditional frameworks, such as PHP-based Laravel, operate on a monolithic MPA model where the server fully renders a new HTML document for every user interaction. While simpler to implement initially (Otwell, 2021), this introduces continuous network latency—often referred to as "page blink"—and increases server load. Fielding (2000), in his seminal thesis on network architectures, argues that tightly coupling the user interface to the server inherently reduces scalability.
Conversely, the SPA model loads a single HTML shell upon the initial request. Subsequent interactions are handled dynamically by JavaScript, which updates the Document Object Model (DOM) seamlessly via asynchronous API calls (Mesbah and van Deursen, 2007). Benchmarks provided by Mikowski and Taivalsaari (2013) indicate that SPAs drastically reduce network payload sizes after the initial load. For an administrative dashboard requiring rapid, repetitive data entry, this desktop-like responsiveness significantly improves efficiency and user satisfaction, as measured by standardized metrics such as the System Usability Scale (SUS) (Brooke, 1996).

React.js was selected over its competitors due to its rigorous adherence to Component-Based Software Engineering (CBSE) principles. Szyperski (2002) and Sommerville (2016) argue that CBSE enhances maintainability by encapsulating complex logic into isolated, reusable units. Furthermore, React circumvents the performance bottlenecks of traditional DOM manipulation by utilising a "Virtual DOM" algorithm. Instead of updating the browser's slow DOM directly, React calculates state differences in memory and selectively re-renders only the changed elements (Gackenheimer and Mardan, 2015). This architectural choice is highly performant and specifically suited for rendering the large, dynamic data tables required in a school administration system.
2.3.4 Server-Side Runtime Environments: Thread-Based versus Event-Driven
The choice of server-side runtime fundamentally dictates how a web application handles concurrent user traffic. Traditional environments, such as Java or PHP, operate on a thread-based model, spawning a new operating system thread for each incoming HTTP request. While highly effective for CPU-intensive calculations, this model suffers from significant memory overhead and thread-blocking when waiting for database queries to resolve (Goetz et al., 2006).
In contrast, Node.js utilises an event-driven, single-threaded, non-blocking Event Loop architecture (Tilkov and Vinoski, 2010). When an I/O operation is triggered, Node.js offloads the task and continues processing other incoming requests, executing a callback only when the database responds (Casciaro, 2014). Research conducted by Chitra and Satapathy (2017) demonstrated that Node.js provides up to 50% higher throughput than Java in strictly I/O-bound applications. Given that a school administration system spends the vast majority of its execution time reading and writing database records rather than performing heavy mathematical computations, Node.js represents the optimal runtime environment.
2.3.5 Database Strategy: The CAP Theorem and NoSQL
The database layer requires a critical choice between traditional Relational SQL databases (e.g., MySQL) and Document-oriented NoSQL stores (e.g., MongoDB). This decision is best analysed through the lens of the CAP Theorem, which states that a distributed data store can only simultaneously provide two of three guarantees: Consistency, Availability, and Partition Tolerance (Brewer, 2012).
SQL databases prioritise strict ACID consistency, relying on rigid, tabular schemas. However, they suffer from the "Object-Relational Impedance Mismatch"—the inherent difficulty of translating object-oriented programming structures into flat database tables (Date, 2004). Schema migrations in SQL are notoriously complex and can severely slow down agile development cycles. MongoDB, conversely, stores data as flexible BSON (Binary JSON) documents. Comparative studies by Boicea et al. (2012) and Han et al. (2011) demonstrate that JSON-native formats eliminate the impedance mismatch, mapping perfectly to the JavaScript objects used in both Node.js and React. This flexibility accelerates the development of the Minimum Viable Product (MVP) and allows for rapid iteration of the student data model as requirements evolve.
2.3.6 Security Architecture: Application Hardening and the CIA Triad
A professional system must guarantee absolute trustworthiness and robustness, particularly when handling data involving minors. The security architecture of the proposed system is meticulously mapped against the foundational CIA Triad: Confidentiality, Integrity, and Availability (Pfleeger and Pfleeger, 2006), specifically addressing vulnerabilities identified by the Open Web Application Security Project (OWASP, 2021).
Confidentiality ensures that data is exclusively accessed by authorised personnel. To achieve this, the system implements application hardening by discarding traditional, stateful session cookies in favour of stateless JSON Web Tokens (JWT). Furthermore, robust Role-Based Access Control (RBAC) middleware is implemented to explicitly prevent "Broken Access Control," the primary threat in the OWASP Top 10. Passwords are secured using advanced cryptographic hashing algorithms (Bcrypt) to mitigate credential theft.
Integrity and Robustness ensure that data remains accurate and protected from malicious tampering. Traditional systems are frequently vulnerable to Injection Attacks (OWASP A03). To mitigate this, the system employs rigorous Defensive Programming techniques. Mongoose Object Data Modeling (ODM) is utilised to strictly sanitize, cast, and validate all incoming network payloads before they reach the database, effectively neutralizing NoSQL injection vectors (Tajpour et al., 2011). Additionally, while legacy applications built on lower-level languages like C/C++ are susceptible to catastrophic buffer overflow attacks (where inputs exceed allocated memory variables), the use of a high-level interpreted language like JavaScript fundamentally mitigates this memory-management risk. Furthermore, React's JSX syntax automatically escapes embedded data, providing a robust, built-in defence against Cross-Site Scripting (XSS) attacks (Johns et al., 2008).
Availability and Digital Forensics ensure the system remains operational and auditable. By deploying the application via a modern cloud platform, the system mitigates the risk of localized Denial of Service (DoS) attacks. Furthermore, to support post-incident digital forensics—a critical component of modern security responses—the system will implement comprehensive application logging, ensuring a traceable audit trail of all administrative actions.
2.3.7 Cloud Deployment Models and Sustainable IT
The physical deployment of the application requires selecting an appropriate infrastructure model as defined by the National Institute of Standards and Technology (Mell and Grance, 2011). Traditional Infrastructure as a Service (IaaS), such as raw AWS EC2 instances, provides maximum control but requires time-consuming manual operating system patching and security configurations. Therefore, a Platform as a Service (PaaS) model has been selected. This abstracts the server layer, allowing development efforts to remain entirely focused on application logic.
Crucially, the shift toward cloud computing carries significant environmental implications. Moving away from energy-inefficient, on-premise school servers toward multi-tenant Cloud PaaS environments drastically reduces the overall carbon footprint. Research by Garg and Buyya (2012) indicates that cloud providers optimise their server utilisation rates compared to the vast energy waste of local servers. This architectural choice directly aligns the project with modern, sustainable IT practices and "Green Computing" initiatives (Murugesan, 2008).

2.4 Methodological Review
2.4.1 Traditional Software Development Life Cycles
To satisfy Learning Outcome 1, the methodology used to manage the project must be critically justified. The traditional Waterfall model, originally formalised by Royce (1970), mandates a rigid, sequential progression through requirements, design, implementation, and testing. Sommerville (2016) heavily critiques this approach, arguing that "Big Design Up Front" is fundamentally flawed when dealing with volatile software requirements. In the context of a student project, adhering strictly to Waterfall is exceptionally high-risk; if a misunderstanding regarding a user interface requirement occurs in Week 1, it may remain entirely undiscovered until the final testing phase, leaving no time for remediation.
2.4.2 Agile Methodologies and their Limitations
In response to the rigidities of Waterfall, Agile methodologies (Beck et al., 2001)—specifically the Scrum framework—have become the industry standard, prioritising continuous delivery and extreme flexibility. However, Schwaber and Sutherland (2020) explicitly design Scrum for cross-functional teams rather than individual developers. The administrative overhead of mandatory Scrum ceremonies, such as daily stand-ups and sprint retrospectives, can act as a severe bottleneck. As Kniberg (2015) notes, applying strict team-based Agile rules to a solo developer often induces "process fatigue," stripping away the efficiency that Agile is meant to provide.
2.4.3 Justification for the Hybrid Development Methodology
Recognising the extremes of both Waterfall and pure Agile, this project adopts a pragmatic Hybrid Methodology, drawing inspiration from iterative frameworks such as the Rational Unified Process (Kruchten, 2003) and tailored approaches theorised by Boehm and Turner (2003). The backend architecture (the Database and API) will be developed using an Incremental approach. This borrows the structural discipline of Waterfall, ensuring that the foundation, security protocols, and data integrity layers are completely stable before any frontend interface is attached.
Conversely, the frontend user interface will be developed via Iterative Prototyping. Acknowledging that UI design is a process of discovery, wireframes will be rapidly converted into code, evaluated against usability heuristics, and refined in continuous cycles. This hybrid approach perfectly aligns with the "Lean Startup" philosophy championed by Ries (2011), focusing exclusively on delivering a functional Minimum Viable Product (MVP) within the strict constraints of the academic deadline.
2.4.4 Software Testing Paradigms and Quality Assurance
Ensuring the trustworthiness of the final artifact requires a rigorously defined testing strategy (Myers et al., 2011). While strict Test-Driven Development (TDD)—where tests are written before the application code—offers the highest level of software verification, it presents a significant learning curve that can derail strict development timelines. Therefore, this project adopts a pragmatic Automated Unit Testing strategy utilising the Jest testing framework. Tests will be written concurrently alongside critical business logic (such as cryptographic password hashing and automated grade aggregation) to verify system robustness. This approach provides the safety net of TDD without the prohibitive initial overhead, successfully balancing software quality assurance with project time constraints.
2.5 Synthesis: Conceptualising the Solution
The critical analysis of the literature confirms a stark market failure: small educational institutions are caught in a damaging digital divide. They are forced to choose between unaffordable, proprietary Enterprise ERPs that result in vendor lock-in, and highly insecure, ad-hoc spreadsheet methods that violate modern data protection laws.
To bridge this gap, the proposed artifact is a bespoke, lightweight School Administration System engineered using the MERN stack. By integrating a Component-Based UI (React) for usability, an Event-Driven backend (Node.js) for high concurrent throughput, and a NoSQL document store (MongoDB) for agile schema flexibility, the system will effectively eliminate institutional data silos. Ultimately, this approach will democratise access to ERP-grade data integrity via ethical Open-Source technologies, ensure strict trustworthiness and GDPR compliance through CIA Triad security principles and defensive programming, and promote public well-being by delivering an accessible interface that reduces administrative burnout. These synthesized findings establish the technical blueprint for the project, directly informing the feature set that will be prioritised using the MoSCoW methodology in the subsequent Requirements Analysis chapter.

3.2 Requirement Analysis and Elicitation
In professional software engineering, accurate requirements elicitation is critical to ensuring the final artifact delivers tangible business value. Because this project addresses a broad, sector-wide issue—the digital divide and data fragmentation in educational institutions rather than a single bespoke client, requirements were systematically gathered through a synthesis of the literature review and a competitive analysis of existing products.
As established in Chapter 2, the critical analysis of existing systems such as Capita SIMS and Moodle revealed a distinct gap in the market: small institutions require the relational data integrity of an Enterprise Resource Planning (ERP) system without the associated feature bloat and prohibitive costs. 3.3 Functional and Non-Functional Requirements
To ensure the timely delivery of a functional Minimum Viable Product (MVP) within the strict constraints of the academic deadline, the elicited requirements were subjected to rigorous prioritisation. The MoSCoW method—an acronym representing Must have, Should have, Could have, and Won't have—was adopted for this purpose. 3.3.1 Functional Requirements
Functional requirements dictate the specific behaviours and operational capabilities the system must execute. To maintain a user-centric development focus, these requirements were formulated as Agile User Stories. The foundational tier of the application demands secure access and robust data management. It was determined that an administrator must be able to securely authenticate their identity to ensure that unauthorised users cannot access sensitive educational records (Must Have). Upon authentication, the system must facilitate full Create, Read, Update, and Delete (CRUD) operations. Specifically, the administrator must be able to create and store new student profiles and dynamically enroll students onto specific academic courses, with backend logic actively preventing duplicate enrollments (Must Have).
Following the establishment of the core database, the system must facilitate daily academic operations. It was specified that the administrator should be able to record daily attendance using a binary toggle interface, allowing the institution to meet statutory monitoring requirements (Should Have). Additionally, the system should allow the input of numeric grades for academic assignments, automatically calculating passing or failing statuses based on predefined institutional thresholds (Should Have). Conversely, to aggressively manage project risk, certain features were explicitly descoped. It was decided that the system will not have the capability to export student data to complex, formatted PDF reports within the initial MVP iteration, ensuring development resources remain focused on core database stability (Won't Have).
3.3.2 Non-Functional Requirements
While functional requirements define system behaviour, Non-Functional Requirements (NFRs) define the underlying quality, security, and operational constraints of the architecture. These constraints were systematically formulated in strict alignment with the ISO/IEC 25010 standard for software quality evaluation, which provides a comprehensive framework for specifying software product quality (ISO, 2011; Hidayati et al., 2021).
Aligning with the confidentiality pillar of the CIA Triad, it is mandated that passwords must never be stored in plaintext; they must be cryptographically hashed prior to database insertion, and all API endpoints must be protected against unauthorised access. Regarding performance efficiency, the client-side dashboard must retrieve and render critical data from the server efficiently, aiming to achieve rapid load times to prevent administrative bottlenecking. In terms of usability, the interface must adhere to minimalist design heuristics to deliberately reduce extraneous cognitive load, adapting seamlessly to various screen sizes (Sweller, 1988). Finally, regarding reliability, the backend server architecture must implement centralized error handling, ensuring that invalid data inputs are caught and sanitized without causing the server process to crash.
3.4 Software Development Life Cycle (SDLC)
To govern the translation of these requirements into a functional product, an appropriate Software Development Life Cycle (SDLC) must be defined. Recognizing the extreme rigidities of the traditional Waterfall model and the high administrative overhead of pure Agile frameworks like Scrum, this project adopts a Hybrid Methodology tailored for an individual developer (Boehm and Turner, 2003).
The architecture is divided into two distinct life cycle streams. The backend system—comprising the database schemas and the server-side API—follows a highly structured, incremental approach. This ensures that the foundational security protocols and data integrity rules are rigorously defined and thoroughly tested before any external access is permitted. Conversely, the frontend user interface is developed via iterative prototyping. Wireframes are designed, evaluated against usability heuristics, and converted into React components in continuous cycles. This hybrid life cycle ensures that the system's core is robust and secure, while the user-facing elements remain flexible enough to undergo necessary usability refinements.
3.5 System Architecture, Components, and Communication
To satisfy the requirement of utilising established technical frameworks, the project adopts a modern Three-Tier Architecture, leveraging the MERN stack (MongoDB, Express.js, React.js, Node.js) to separate the application into distinct, highly maintainable components.
The architecture fundamentally relies on the Model-View-Controller (MVC) paradigm to enforce the separation of concerns (Fowler, 2003). The Presentation Layer, functioning as the View, is engineered using React.js and operates entirely within the user's browser. It is strictly responsible for rendering the interface and capturing user inputs. The Application Layer, functioning as the Controller, is engineered using the Node.js runtime and the Express.js framework. This intermediate server layer acts as the secure gateway, intercepting requests, enforcing authentication middleware, and processing business logic. Finally, the Data Layer, functioning as the Model, is engineered using MongoDB, a NoSQL document database responsible for persistent storage.
Communication between these isolated components is achieved via a Representational State Transfer (REST) API architecture (Fielding, 2000). When the React frontend requires data, it initiates an asynchronous HTTP request (e.g., a GET or POST request) to a specific endpoint exposed by the Express server. The server queries the database, retrieves the necessary records, and transmits the response back to the client over the network. Crucially, all data exchange between the client and the server is formatted as JavaScript Object Notation (JSON). JSON was selected as the standard data payload format because it is lightweight, human-readable, and inherently compatible with both the JavaScript-based frontend and the document-oriented structure of the NoSQL database, thereby eliminating the data parsing bottlenecks associated with older XML-based architectures.

3.6 Database Design and Data Storage
The data storage mechanism fundamentally diverges from traditional relational databases. MongoDB stores data as flexible, schema-less BSON (Binary JSON) documents within collections, rather than rows within rigid tables. However, storing highly sensitive educational data without structural rules poses a severe integrity risk. To resolve this vulnerability, strict schema validation is enforced at the application level using the Mongoose Object Data Modeling (ODM) library.
The data model is engineered to eliminate the redundancy typically found in spreadsheet-based "data silos." The system relies on reference-based relationships, utilising unique ObjectIds to dynamically link distinct documents. The primary entities include the User entity for administrative access, the Student entity for capturing personal demographics and GDPR consent flags, and the Course entity for defining academic modules. To resolve the complex many-to-many relationship between students and the courses they take, an Enrollment entity acts as a relational bridge. Finally, a Grade entity records academic performance, linking specific students and courses to numeric scores to ensure an immutable audit trail.
